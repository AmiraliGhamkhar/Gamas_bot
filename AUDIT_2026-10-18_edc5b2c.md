## 1. Executive summary

The code is substantially better than its own documentation. Lint, typing and the 514-test suite all pass
as CI runs them, the media pipeline is genuinely isolated in a child process with a hard, group-wide
kill, the OOXML reader really does validate entry count, unpacked size, absolute paths, `..` and symlink
entries, the receipt path check is symlink-aware, and the "raw transcript before notes" promise is
implemented in that order in both the media and presentation pipelines (including settle-after-delivery).

The defects that matter are in the **money path and the migration path**, not in the media or text
engineering:

1. **The v2→v3 importer refuses legitimate databases.** Its self-verification compares the v3 derived
   balance against a v2 sum that includes entitlements the importer deliberately skips (expired) and
   ignores the century-credit it grants to unlimited users. Both cases abort with
   `balance verification failed` after reproduction. A migration that cannot run is an operational
   blocker for the documented upgrade path.
2. **A payment can be approved and credit nothing.** Approval credits `plan["hours"]` from the *current,
   active* plan row; if the plan was deactivated (or deleted) between purchase and review, the bot
   passes `hours = 0`, marks the payment `approved`, notifies the user that credit was added, and writes
   an audit row saying it was approved. Reproduced: `status=approved`, `credited seconds: 0`.
3. **The ledger's write lock is not actually universal.** `Database.release_hold` writes and commits
   outside `_write_lock`, so it can commit another coroutine's uncommitted statements. Reproduced: a
   pending ledger insert became visible to a second connection immediately after `release_hold`. The
   realistic harm is a settled debit being committed while its hold is still open (double charge after
   restart), plus a violation of the "settles or releases, exactly once" invariant under interleaving.

Secondary themes: several security controls asserted in `docs/SECURITY.md` do not exist (ban enforcement,
admin-credit protection, one-open-payment unique index, receipt-directory startup verification); the
Free Office promise "your text, exactly" is broken by numeric coercion (leading zeros) and dropped rule
lines; crashed jobs leak temp directories because the documented startup cleanup is absent; and receipt
retention never runs on a bot that restarts at least daily.

Overall verdict: **sound architecture, good engineering discipline, weak accounting/migration edges and
documentation that repeatedly claims controls the code does not implement.** No remote code execution,
no cross-user data access and no authentication bypass were found.

### The three risks that matter most

| # | Risk | Why it matters |
| --- | --- | --- |
| 1 | Payment approval derives credit from the live plan row (F-02) | Money is taken and nothing (or the wrong amount) is delivered, with an audit trail that says success |
| 2 | v2 import aborts on ordinary legacy data (F-01) | The advertised migration path cannot be completed; operators may migrate by hand and lose balances |
| 3 | `release_hold` outside the write lock (F-03) | Breaks the accounting atomicity the whole billing model is documented to guarantee |

## 5. Findings register — confirmed defects

Severity is business impact if the preconditions occur, not likelihood alone. "Confidence" is confidence
in the *defect*, not in the reachability of the worst outcome.

**High severity**

### F-01 — v2 importer aborts on expired entitlements and on unlimited users

* **Severity:** High · **Confidence:** High (reproduced twice)
* **Location:** `scripts/import_v2.py:256-267` (expected sum), `:270-278` (century credit), `:283-305` (verification)
* **Path / preconditions:** run `python scripts/import_v2.py --from <v2 db> --into <v3 db>` on a real v2
  database. Two ordinary conditions trigger it: (a) an `entitlements` row with `status='active'` whose
  `expires_at` is in the past (the importer skips it when building the ledger, but counts it in
  `expected`); (b) any user with `is_unlimited=1` that also has an active entitlement (the century credit
  is added to `derived` but not to `expected`).
* **Impact:** the import raises `SystemExit`, rolls back and reports failure. Balances are not corrupted,
  but the documented upgrade path cannot be completed. An operator under time pressure may hand-migrate.
* **Evidence:** R1/R2 above. The two sums are computed by different predicates:
  `expected` = `SUM(remaining_seconds) WHERE user_id=? AND status='active'` (no expiry filter),
  ledger rows skip `expiry <= now`, and the unlimited credit at `:270-278` is not in `expected`.
* **Fix:** derive `expected` with the same predicate the ledger replay uses (active, not expired), compare
  only for users that did not receive the unlimited credit, and exclude the century row from the
  comparison. Better: count unlimited users separately and assert `derived - imported_credit == expected`.
* **Regression test:** build a v2 fixture with (i) an expired active entitlement, (ii) an unlimited user
  with a live entitlement; assert `import_v2()` returns 0 and the derived balance equals the v2 remaining
  balance for the non-special user.

### F-02 — Payment approval credits zero (or a changed amount) after the plan is deactivated or edited

* **Severity:** High · **Confidence:** High (reproduced)
* **Location:** `gamas_bot/bot.py:1848-1856` (`plan = await self.db.plan(...)`, `hours = plan["hours"] if plan else 0`),
  `gamas_bot/db.py:555-561` (`plan()` filters `active = 1`), `gamas_bot/db.py:593-635`
* **Path / preconditions:** a user creates a payment for a plan; before an admin reviews it the plan is
  deactivated (`active=0`) or removed, or its `hours`/`validity_days` are edited. The admin taps ✅.
* **Impact:** `review_payment` marks the payment `approved`, inserts a ledger credit of
  `round(plan_hours*3600)` (0 when the lookup fails), notifies the user "✅ پرداخت شما تایید شد:
  ۰ ساعت اعتبار اضافه شد", and writes `payment_approved` to the audit table. Money is taken, nothing is
  delivered, and the audit trail says success. If `hours` was edited, the user receives the new amount,
  not the one advertised at purchase. `payments` has no snapshot of the purchased hours/price.
* **Evidence:** R4: `plan lookup after deactivation: None`, `approval credited seconds: 0`,
  `status: approved`.
* **Fix:** snapshot `hours`, `price` and `validity_days` on the `payments` row when it is created and
  credit from that snapshot; refuse approval (or require an explicit admin override) when the plan row
  is missing. Never credit 0 for an approved paid request. Add a schema check `CHECK (status !=
  'approved' OR credited_seconds > 0)` once the column exists.
* **Regression test:** create a payment, deactivate the plan, approve it; assert either rejection with a
  clear admin message or credit equal to the snapshot — never `approved` + 0.

### F-03 — `release_hold` writes and commits outside the database write lock

* **Severity:** High · **Confidence:** High on mechanism (reproduced), Medium on end-to-end harm
* **Location:** `gamas_bot/db.py:513-520`; compare `_write`/`_write_many` `:152-163` and `settle_hold`
  `:473-511`
* **Path / preconditions:** two jobs finish at nearly the same time (normal with `MAX_ACTIVE_JOBS=3`):
  worker A runs `settle_hold`, which executes the debit INSERT and then awaits its commit; worker B runs
  `release_hold` for a different submission, executes and commits on the same `aiosqlite` connection.
  Because `release_hold` does not take `_write_lock`, B's commit commits A's pending INSERT as well.
* **Impact:** A debit can become durable while A's hold update is not. If the process is killed before
  A's commit, restart recovery releases the hold but cannot undo the debit — the user is charged twice
  (debit + a hold that was released) for one job. It also means a failure path can commit a success
  path's debit, which is exactly the "never both" invariant `BILLING.md` promises. SQLite's own
  file-level journaling is fine; the bug is at the transaction-boundary level.
* **Evidence:** R7 — a deliberately uncommitted ledger row was invisible to a second connection before
  `release_hold` and visible immediately after it.
* **Fix:** acquire `_write_lock` in `release_hold` (and use a single explicit transaction for
  settle/release). Consider `BEGIN IMMEDIATE` for the ledger pair, and make `_apply_migrations`
  exclusive for the same reason.
* **Regression test:** under a lock-aware test double, interleave `settle_hold(A)` and `release_hold(B)`
  while forcing a yield between A's INSERT and COMMIT; assert A's debit is not visible before A
  commits (second connection), and a simulated crash cannot leave a debit with an open hold.

**Medium severity**

### F-04 — The free plan can be granted more than once

* **Severity:** Medium · **Confidence:** High (reproduced)
* **Location:**  `gamas_bot/db.py:398-408`; call site `gamas_bot/bot.py:440-446`
* **Path / preconditions:** two handlers for the same user run concurrently — two `/start` messages, or
  `/start` plus a `menu:main` callback (Telethon dispatches each event as its own task). Both pass the
  `SELECT 1 FROM ledger ... note='free_plan'` check before either inserts.
* **Impact:** N × 1 hour free credit. Reproduced with 10 concurrent calls → 10 rows, 36 000 s. The
  "never renewed by `/start`" promise (`BILLING.md`) and every balance-derived report are affected.
* **Fix:** make it a single atomic statement, e.g.
  `INSERT INTO ledger ... SELECT ... WHERE NOT EXISTS (SELECT 1 FROM ledger WHERE user_id=? AND note='free_plan')`
  and inspect `rowcount`, or add a unique partial index on `(user_id)` where `note='free_plan'`.
* **Regression test:** `asyncio.gather` 10 × `grant_free_plan_once`; assert exactly one `True` and
  3 600 s.

### F-05 — The `banned` flag is never enforced

* **Severity:** Medium · **Confidence:** High
* **Location:** `gamas_bot/db.py:177-180` (`set_banned`, no caller in the package), `gamas_bot/bot.py:838-846`
  (`_handle_message` calls `ensure_user` and discards the returned `banned`), `gamas_bot/bot.py:1898`
  (display only)
* **Path:** any banned user sends a message or taps a callback; every handler proceeds.
* **Impact:** `docs/SECURITY.md:42` promises refusal at the message and callback layers. A user an
  operator believes is blocked can still upload media, spend credit, buy plans and use Free Office.
  There is also no admin command to ban anyone, so the flag can only be set by direct SQL — which is
  why this is latent rather than exploited.
* **Fix:** check `ensure_user(...).banned` at the top of `_handle_message` and `_handle_callback`, reply
  once and return; add `/ban`/`/unban` (admin-only, audited) or delete the flag and the doc claim.
* **Regression test:** set `banned=1` directly, send `/start` and a callback; assert no menu, no
  submission row and one refusal message.

### F-06 — Admin credit grants are not protected; the documented ban/modify guards do not exist

* **Severity:** Medium · **Confidence:** High
* **Location:** `gamas_bot/bot.py:2004-2030` (`/grant`), `:2032-2070` (`/unlimited`)
* **Path:** any admin sends `/grant <another_admin_id> 10000`. The only guard in `_admin_unlimited` is
  "target is not an admin"; `/grant` has none, and no ban command exists.
* **Impact:** `docs/SECURITY.md:43` states the bot refuses to grant credit to another admin — false.
  A compromised or rogue admin can mint credit for a peer; there is no separation of duties and no
  confirmation step. (`/grant` caps at 10 000 hours, which is still ~4× the largest plan.)
* **Fix:** enforce a single `_assert_can_modify(actor, target)` in both commands, require a second
  confirmation for grants above a threshold, and add the missing ban command (or remove the claims).
* **Regression test:** admin A runs `/grant B 5` where B is an admin → refused, no ledger row; same for
  `/unlimited`.

### F-07 — The documented startup cleanup of crashed temp directories does not exist; orphan workers survive parent death

* **Severity:** Medium · **Confidence:** High
* **Location:**  `gamas_bot/bot.py:297-315` (`run()` — no temp sweep), `:1018-1090` (`_run_job` — per-job
  `rmtree` only), `gamas_bot/media.py:63-72` (`start_new_session=True`)
* **Path:** `kill -9`, OOM kill or power loss while a job is running. The `finally` never runs; the
  `submission-*` directory (up to `MAX_FILE_SIZE` + deck media, i.e. multi-GB) stays forever. A media
  worker already running is in its own session and is not killed by the parent's death; it finishes or
  runs to its timeout with no parent to enforce it.
* **Impact:** unbounded disk growth on a long-lived host; `docs/MEDIA.md:52` explicitly claims
  "stale `submission-*` / `deck-*` directories from a crash are removed at startup", so the operator
  will not look for them. Repeated crashes on a 2 GB upload budget can fill the partition and take the
  bot and the database down.
* **Evidence:** no `glob("submission-*")`/`rmtree` outside `_run_job`; grep over the package returns only
  the per-job call.
* **Fix:** on startup, after taking the instance lock, delete `TEMP_DIR/submission-*` (and any
  `deck-*`) older than the process start; optionally record the worker pid and kill its process group
  during recovery. Bound the sweep by mtime and never follow symlinks.
* **Regression test:** create `TEMP_DIR/submission-99-x` and a fresh unrelated file, run the startup
  routine, assert the stale dir is gone and the unrelated file survives.

### F-08 — Receipt retention never runs on a bot that restarts at least daily

### F-09 — Excel export destroys leading zeros and long numeric identifiers

* **Severity:** Medium · **Confidence:** High (reproduced)
* **Location:** `gamas_bot/office.py:89` (`_NUMBER_PATTERN`), `:313-320` (`_cell_value`)
* **Path:** a Free Office Excel request whose text contains a phone number, national ID, student number,

* **Impact:** the cell becomes a float/int (`9123456789`, `7`); the displayed value differs from what the
  user wrote and from the PDF/Word rendering of the same text. `docs/OFFICE.md` documents numeric
  coercion, but not the loss of the leading zero — which is the normal shape of an Iranian mobile number

* **Fix:** keep any digit string whose leading character is `0` (or that exceeds 15 digits) as text;

* **Regression test:** `09123456789`, `007`, `1.5`, `120/80`, `۵۰۰` → only `1.5` becomes numeric; the rest

### F-10 — Free Office text uploads are downloaded before any size check, outside the job queue

* **Severity:** Medium · **Confidence:** High
* **Location:** `gamas_bot/bot.py:601-620` (classification), `:646-683` (`_download_office_text`)
* **Path:** any user sends a `.txt`/`.csv`/`.log` document of any size Telegram allows (up to the bot's
  own 2 GB cap, and Telegram's document limit). The handler downloads it to `TEMP_DIR` in
  `_handle_office_message`, which runs in the Telethon task — before the bounded queue — and only then

* **Impact:** concurrent messages from one or many users can write unbounded bytes to the data
  partition without occupying a queue slot or an active-job slot; `MAX_ACTIVE_JOBS`/`MAX_QUEUED_JOBS` do

  non-text extensions earlier. Optionally route the download through the same semaphore as media work.
* **Regression test:** a message with `file.size = 2 GB` and a `.txt` name must be refused with no

### F-12 — SQLite file permissions are entry-point dependent

* **Severity:** Medium · **Confidence:** High (reproduced)
* **Location:**  `gamas_bot/db.py:92-135` (`connect`), `gamas_bot/__main__.py:95-97` and `:126-128`

### F-17 — A failed note chunk leaves sibling provider requests running

* **Severity:** Low · **Confidence:** High (static)
* **Location:** `gamas_bot/notes.py:1640-1643`
* **Path:** several transcript chunks are mapped concurrently with `asyncio.gather`; one raises
  (`LLMError`, etc.) while others are still in flight.
* **Impact:** `gather` propagates the first failure but does not cancel the siblings, so they continue
  consuming provider quota and the shared HTTP session after the job has failed and its reservation has
  been released. They are not tracked, so shutdown cannot cancel them; if one later raises, the asyncio
  exception handler logs it with no job context. Bounded (`NOTE_CONCURRENCY` ≤ 8), so this is waste, not
  a leak of jobs.
* **Fix:** keep the tasks and cancel them on the first failure (`asyncio.TaskGroup` on 3.11+, or
  `gather(..., return_exceptions=True)` plus explicit cancellation), or wrap each map call so failures
  are collected and the remaining work is still awaited.
* **Regression test:** two chunks, one failing fast and one blocked; assert the blocked one is cancelled
  and no provider call is made after the job fails.

### F-18 — Admin broadcast sends rendered HTML without `parse_mode`, and is an N+1 scan with no hard cap

* **Severity:** Low · **Confidence:** High

## 7. Optional improvements (not defects)

* **Ledger sum performance**: `available_seconds` runs three aggregate subqueries on every menu render and
  per user in `list_users`; a covering index on `(user_id, kind, expires_at)` and a cached balance would
  make admin screens and broadcast preparation O(1).
* **Retention for `transcriptions`**: transcripts are kept forever (privacy claim says "so a job can be
  audited", but no retention policy exists). Consider a configurable retention and a documented backup
  policy.
* **Presentation `skipped` reasons** are appended to the raw transcript delivered to the user; keep them
  in the job log only, or label them distinctly, so the artifact stays the transcript.
* **`_office_last` cache** holds the full text of the last document for up to 500 users in memory with a
  30-minute TTL; a bounded LRU keyed by user with the same TTL would make the memory bound explicit.
* **Receipt display**: send a thumbnail/`photo` with a size cap rather than forwarding the original at up
  to 5 MB per admin view.
* **CI**: pin actions by commit SHA; make `pip-audit` blocking for runtime deps, or at least fail on
  `high`; add `--strict` to `sync_requirements --check` in the docs.
* **Mypy scope**: 12 of 26 modules are checked. Add `bot.py`, `db.py`, `notes.py`, `stt.py`, `llm.py`,
  `presentations.py`, `office.py` incrementally; the current gate would not catch a type regression in
  the money path.
* **Test count in docs**: generate the coverage table from the test tree (see F-23).

## 10. The three highest-value missing tests

1. **Payment approval integrity** (`tests/test_db_billing.py`): create a payment, deactivate/remove its
   plan, approve it; assert the payment is not credited 0 and that the credited seconds come from the
   purchase-time snapshot (covers F-02, F-14, F-16).
2. **Ledger transaction isolation** (`tests/test_db_billing.py` or a new `test_db_atomicity.py`): force a
   yield between `settle_hold`'s INSERT and COMMIT while `release_hold` runs for another submission;
   assert the debit is invisible until its own commit, and a simulated crash cannot leave a debit with an
   open hold (covers F-03, the accounting invariant).
3. **Restart and cancellation recovery at the bot level** (`tests/test_bot.py`): cancel `_run_job` while a
   hold is open and while a temp workdir exists; assert the hold is released exactly once, the submission
   is `failed`, the temp directory is gone, and a following `recover_interrupted()` is a no-op (covers
   F-07, the shutdown promise, and the cancellation path that `test_jobs.py` currently tests only at the
   queue level).
