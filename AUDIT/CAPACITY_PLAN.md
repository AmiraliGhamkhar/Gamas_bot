# گزارش بهبود ظرفیت هم‌زمانی — رسیدن به ۱۰۰٪ پتانسیل

تاریخ: ۱۴۰۵/۰۹/۰۷ · شاخه: `arena/3cfff6d1-gamas-bot` · مبنای عدد و رقم: بنچمارک واقعی روی
همان استک production (WSGI + SQLite WAL + اعتبارسنجی initData) در همین محیط.

---

## ۱) خط پایه (امروز — اندازه‌گیری‌شده)

| سنجه | مقدار |
| --- | --- |
| هزینهٔ هر درخواست API | **20.6ms** (p50 19.5 / p95 27.5) |
| توان هر worker تک‌رشته (مثل Passenger) | **~48 req/s** |
| سقف GIL زیر بار هم‌زمان (۳۰ ترد) | ~40 req/s کل |
| فایل استاتیک (assets هش‌دار) | 1.4ms (~700 rps) |
| JS مینی‌اپ روی سیم | 203KB خام (نسخه gzip فقط 65KB — **سرو نمی‌شود**) |

**ترکیب هزینهٔ ۲۰ms هر درخواست (تفکیک‌شده):**

| جزء | هزینه |
| --- | --- |
| `Database.connect()` + `close()` در هر درخواست | **~17ms (≈85٪)** |
| `from_env()` در هر درخواست | ~0.4ms |
| خودِ کوئری‌ها (۲–۴ خواندن) | **~0.2ms** |
| HMAC + JSON + WSGI | ~1–2ms |

یعنی **۸۵٪ توان سرور صرف باز و بسته کردن اتصال دیتابیس می‌شود، نه کار واقعی.**
جزئیات: `webapp_api.py` در هر درخواست `Database(...)` تازه می‌سازد و `connect()` آن
(در `db_core.py:269`) دو کانکشن aiosqlite (۲ ترد)، ~۱۳ PRAGMA، اجرای migrations و
`commit` را از نو انجام می‌دهد — در حالی که `user_identity` فقط **0.22ms** طول می‌کشد.

## ۲) آزمایش «بعد از اصلاح» (پروتوتایپ connection-reuse)

یک نمونهٔ اولیه (کش‌کردن یک `Database` به‌ازای هر فایل دیتابیس) ساخته و همان سنجه‌ها
دوباره اندازه‌گیری شد:

| سنجه | قبل | بعد (پروتوتایپ) | بهبود |
| --- | --- | --- | --- |
| هزینهٔ هر درخواست | 20.6ms | **0.3–0.4ms** (خودِ DB) | **~50×** |
| توان هر worker | ~48 rps | **~250–400 rps** (با سربار WSGI/HMAC/JSON) | **5–8×** |

⚠️ نکتهٔ فنی مهم در طراحی اصلاح نهایی (دلیل هنگ پروتوتایپ هم‌زمان): اتصالِ aiosqlite
به‌ازای هر فراخوانی، future را روی **event loop در حال اجرای همان لحظه** می‌سازد
(`aiosqlite/core.py:127`)؛ اشتراک یک اتصال بین **چند loop هم‌زمان** ایمن نیست. پس اصلاح
درست این است:

> **یک event loop دائمی به‌ازای هر پروسه + یک `Database` روی همان loop + ارجاع درخواست‌ها
> با `asyncio.run_coroutine_threadsafe`** (یا معادل ساده‌تر: استخر اتصال per-loop).
> این الگو هم ۵۰ برابر سریع‌تر است و هم ترد-ایمن.

## ۳) نقشهٔ بهبود (به ترتیب اولویت)

### فاز ۱ — برد سریع، بدون تغییر معماری (هفتهٔ ۱–۲)

| # | اقدام | اثر تخمینی | سختی |
| --- | --- | --- | --- |
| 1 | **Connection-reuse در `webapp_api.py`** (loop دائمی + DB دائمی per process؛ migrations فقط در startup) | توان API **5–8×**؛ یعنی ~۲۰۰ rps/worker به‌جای ~۴۸ | متوسط |
| 2 | **کش کردن `Settings`** (`from_env()` فقط یک‌بار در هر پروسه؛ در صورت نیاز invalidate با mtime فایل `.env`) | ~0.4ms در هر درخواست + حذف I/O | آسان |
| 3 | **سرو assets فشرده**: فایل‌های `.gz` از build وکنارشان سرو شوند (یا gzip در لایهٔ Apache/nginx) | انتقال 270KB → 75KB (**3.2×**)؛ لود اول مینی‌اپ روی موبایل محسوس | آسان |

### فاز ۴ — فقط اگر واقعاً لازم شد (هزاران کاربرِ همزمانِ نوشتن‌گر)

- مهاجرت SQLite → PostgreSQL (در عمل، با WAL و نوشتن‌های کوتاه، SQLite تا چند هزار
  کاربر همزمان کافی است؛ عجله‌ای نیست).
- صف کارها (job queue) با Redis/RabbitMQ + worker جدا برای scale افقی.
- CDN برای assets (مثلاً jsDelivr/Cloudflare) — کاهش بار هاست برای لود اول.

## ۴) مدل ظرفیت (فرمول‌ها برای برنامه‌ریزی)

```
توان API (rps)      = تعداد_worker × 1000 / هزینهٔ_هر_درخواست(ms)
کاربر همزمانِ فعال   = توان_API / مصرف_هر_کاربر(rps)        # مصرف ≈ 0.2–0.3
توان job (فایل/ساعت) = 3600 / میانگین_مدت_شغل(ثانیه) × MAX_ACTIVE_JOBS
```

| سناریو | هزینه/درخواست | workerها | توان API | کاربر همزمانِ فعال | فایل/ساعت |
| --- | --- | --- | --- | --- | --- |
| **امروز** (cPanel 2GB) | 20ms | 2–4 | ~100–190 rps | ~۳۰۰–۹۰۰ | ~20–35 |
| **بعد فاز ۱** (همان هاست) | ~4ms | 2–4 | ~500–1000 rps | ~۲۰۰۰–۴۰۰۰ | ~20–35 |
| **بعد فاز ۳** (VPS 4GB, 4×4) | ~4ms | 16 thread | ~2000–4000 rps | ~۸۰۰۰+ | ~40–140 |

*اعداد کاربر بر اساس مصرف متوسط کاربر فعال است؛ «همه در یک لحظه» (broadcast) همیشه
صف کوتاه می‌سازد و با فاز ۲ (push) کوچک‌تر می‌شود. اعداد فایل/ساعت با میانگین شغل
۵–۱۰ دقیقه محاسبه شده‌اند.*

## ۶) ریسک‌های اجرای اصلاحات

1. **اتصال مشترک DB باید ترد-ایمن باشد** (نکتهٔ بخش ۲) — حتماً با الگوی loop دائمی یا
   استخر per-loop انجام شود؛ اجرای naive آن (مثل پروتوتایپ این گزارش) زیر بار هم‌زمان
   deadlock می‌دهد.
2. **migrations فقط در startup**: اگر دو پروسه هم‌زمان migrate کنند، SQLite قفل
   `busy_timeout=5s` دارد؛ با اجرای یک‌باره در startup مشکلی نیست.
3. **سازگاری workflow**: هیچ تغییری در قرارداد API لازم نیست؛ تمام ۳۲ بررسی اتصال و
   تست‌های موجود باید مثل قبل سبز بمانند (معیار پذیرش هر PR).
4. **اندازه‌گیری روی هاست واقعی**: قبل/بعد هر فاز، `python -m scripts.concurrency_bench`
   و `python -m scripts.perf_bench` اجرا و نتایج در همین سند ثبت شود.

## ۷) جمع‌بندی

- **بزرگ‌ترین برد با کمترین هزینه:** حذف باز/بسته شدن DB در هر درخواست (85٪ هزینهٔ فعلی)
  → بهبود **5–8 برابری** توان API روی همان هاست، بدون هیچ تغییر سخت‌افزار.
- **دوم:** فشرده‌سازی پاسخ‌های استاتیک (3.2× انتقال کمتر).
- **سوم:** push به‌جای polling و جداسازی pipeline پردازش از API.
- با اجرای فازهای ۱ و ۳، ظرفیت عملی از «~۳۰۰ کاربر همزمانِ فعال» به «**چند هزار کاربر
  همزمانِ فعال + ۱۰۰+ فایل در ساعت**» می‌رسد — یعنی استفادهٔ کامل از پتانسیل سخت‌افزار.

اولین گام پیشنهادی: **PR فاز ۱ (connection-reuse + settings cache)** با معیار پذیرش
«سبز بودن کامل تست‌ها + رسیدن هر درخواست API به زیر 5ms در بنچمارک».
